# Gmail AI Labeler - 아키텍처 및 업데이트 상세 내역 (v2.0 -> v3.0)

이 문서는 기존 확장 프로그램이 기능별로 분산되고 UI/백엔드 로직이 분리되어 있던 문제를 해결하기 위해 진행된 **전면적인 아키텍처 개편 및 기능 구현 사항**을 상세히 기록한 문서입니다. 향후 유지보수 및 기능 확장을 위해 필독을 권장합니다.

---

## 1. 중앙 집중형 설정(Settings) 아키텍처 및 마이그레이션

이전 버전에서는 설정 데이터가 일관성 없이 여러 곳에 저장되고, UI와 백엔드 간 상태 불일치가 자주 발생했습니다. 이를 해결하기 위해 새로운 중앙 집중형 설정 시스템을 구축했습니다.

*   **`settings_schema.js` 및 `settings_defaults.js`**: 9가지 메인 카테고리(General, Connections, Gmail, Calendar, AI, Automation, Notifications, Data, Advanced)로 구성된 엄격한 스키마를 정의했습니다. 기존의 복잡했던 AI 공급자별 관리 방식을 버리고, 통합된 `ai.credentials` 배열 형태로 스키마를 변경했습니다.
*   **`settings_store.js`**: 단일 진실 공급원(Single Source of Truth) 역할을 하는 스토어입니다. Chrome Storage와 동기화되며, `scheduleSave`를 통해 디바운스된(Debounced) 안전한 비동기 저장을 보장합니다.
*   **`settings_migration.js`**: 사용자가 확장 프로그램을 업데이트할 때, 기존 v1, v2의 낡은 스토리지 데이터를 안전하게 v3 스키마(`ai.credentials` 등)로 변환해주는 마이그레이션 모듈입니다. API 키가 콘솔 로그에 노출되지 않도록 보안 처리도 완료되었습니다.

## 2. AI 요청 라우터 및 강력한 페일오버 (AI Request Router & Failover)

Gemini뿐만 아니라 OpenAI, Anthropic 등 다중 LLM을 지원하고 API 호출 제한(Quota/Rate Limit)에 대응하기 위해 AI 엔진을 완전히 재설계했습니다.

*   **`ai_provider_registry.js`**: 사용 가능한 AI 공급자(`google`, `openai`, `anthropic`)와 각 공급자별 세부 모델(예: `gemini-1.5-flash`, `gpt-4o`, `claude-3-haiku-20240307`)을 하드코딩하여 중앙에서 관리합니다.
*   **통합 API 키 관리 (`ai.credentials`)**: 사용자는 우선순위에 따라 여러 공급자의 API 키를 여러 개 등록할 수 있습니다. 
*   **`ai_request_router.js`**: API 요청을 보낼 때 `ai.credentials` 배열을 순회하며 가장 우선순위가 높은(그리고 사용 가능한) API 키를 사용합니다.
*   **`ai_failover_manager.js` 및 `ai_quota_manager.js`**: API 통신 중 `429 Too Many Requests`나 `Quota Exceeded(할당량 초과)` 에러가 발생하면, 즉시 해당 키를 일시 정지(혹은 완전 정지)시키고 다음 우선순위의 API 키(예: Gemini 실패 시 OpenAI로)로 **자동으로 페일오버**하여 백그라운드 작업이 멈추지 않도록 보장합니다.
*   **공급자 어댑터 (`google_provider.js`, `openai_provider.js`, `anthropic_provider.js`)**: 각 LLM의 특성에 맞게 프롬프트와 Structured JSON Output(구조화된 JSON 출력)을 강제하는 어댑터 클래스입니다. 향후 새로운 LLM이 추가되더라도 어댑터만 추가하면 되는 구조입니다.

## 3. 캘린더 통합 백엔드 엔진 완성 (Calendar API Integration)

기존에는 캘린더 UI만 존재하고 실제 Google Calendar와의 연동 로직이 미완성 상태였습니다. Gmail 분류와 완전히 독립된 캘린더 전용 데이터 도메인을 구축했습니다.

*   **`calendar_api.js`**: Google Calendar REST API(`https://www.googleapis.com/calendar/v3/calendars/...`)와 직접 통신하여 이벤트 조회 및 색상(colorId) 업데이트를 수행합니다.
*   **`calendar_classifier.js`**: AI를 사용하여 사용자의 일정 제목, 설명, 시간 등을 분석해 자동으로 적절한 캘린더 카테고리와 색상을 할당하는 프롬프트 엔진입니다.
*   **`calendar_engine.js`**: 백그라운드에서 일정 기간(오늘, 이번 주, 이번 달)의 캘린더 데이터를 가져와 `calendar_classifier`에 넘기고, 그 결과값으로 `calendar_api`를 호출해 실제 캘린더 일정을 일괄 업데이트하는 스케줄러/배치 엔진입니다.
*   옵션 페이지의 **"Generate AI Categories"** 버튼을 통해 사용자가 클릭 한 번으로 초기 캘린더 분류 기준을 자동 생성할 수 있도록 백그라운드 Job 큐와 연동되었습니다.

## 4. 모던 Options UI (설정 페이지) 전면 개편

설정 페이지를 완전히 SPA(Single Page Application) 형태로 개편하여 사용자 경험과 구조를 현대화했습니다.

*   **AI Credential Card UI (`options.html`, `options.js`)**: 기존의 정적인 드롭다운 대신, 여러 개의 API 키를 직관적으로 추가/수정/삭제하고 위아래로 움직여 우선순위를 변경할 수 있는 카드 기반 UI를 도입했습니다.
*   **Test Connection (연결 테스트)**: API 키를 추가할 때, 저장하기 전에 모달창에서 즉시 AI와 통신하여 키가 정상인지 검증하는 기능을 구현했습니다.
*   **i18n 완벽 적용 (`_locales/`)**: UI 템플릿에 하드코딩된 내부 키(예: `aiActiveProvider` 등)를 전부 제거하고, `data-i18n` 속성을 활용해 다국어 처리를 표준화했습니다. 영어(en), 한국어(ko), 일본어(ja), 중국어 간체(zh_CN) 등 4개 국어 번역이 모두 `messages.json`에 반영되었습니다.

## 5. 버그 수정 (v3.0 리팩토링 직후 발견된 런타임 버그 수정)

위 리팩토링 직후 실제로 실행하면 죽는 버그들이 다수 발견되어 함께 수정했습니다.

*   **서비스 워커에서 `window` 전역 등록 실패**: `ai/*.js`, `settings/*.js`의 모듈들이 `typeof window !== "undefined"` 조건으로 전역 객체(`AIProviderRegistry`, `SettingsStore`, `migrateToLatestSettings` 등)를 등록하고 있었는데, MV3 백그라운드 서비스 워커에는 `window`가 없어 아무것도 등록되지 않았습니다. AI 라우터/설정 스토어 전체가 백그라운드에서 동작하지 않던 문제로, `self`를 사용하도록 전부 수정했습니다.
*   **AI 공급자 어댑터 미등록**: `google_provider.js`, `openai_provider.js`, `anthropic_provider.js`가 옵션 페이지(`options.html`)에 스크립트로 포함되어 있지 않아 "Test Connection" 기능이 항상 실패했습니다. 스크립트 태그를 추가했습니다.
*   **`ai.geminiApiKeys` → `ai.credentials` 스키마 불일치**: `background.js`의 `getGeminiApiKeys()`가 더 이상 존재하지 않는 옛 설정 경로(`ai.geminiApiKeys`)를 읽고 있어 항상 빈 배열을 반환, 메일 분류가 "API 키 없음" 오류로 실패했습니다. 새 `ai.credentials` 구조를 읽도록 수정했습니다.
*   **설정 마이그레이션 미실행**: `settings_migration.js`가 `background.js`의 `importScripts` 목록에 없었고, 백그라운드 시작 시점에 호출되지도 않아 옵션 페이지를 열지 않은 사용자는 계속 구버전 설정을 사용했습니다. 임포트 목록에 추가하고 `onInstalled`/`onStartup` 시점에 마이그레이션을 실행하도록 했습니다. 또한 `settings_defaults.js`의 `schemaVersion`이 `2`로 남아있어 마이그레이션이 완료돼도 다시 실행되며 설정을 되돌리던 문제도 `3`으로 맞췄습니다.
*   **캘린더 카테고리 자동 생성 기능 전체 오류**: `calendar_init_categories` 핸들러가 존재하지 않는 `fetchCalendarEvents`/`fetchCalendarColors` 함수를 호출하고 있었고(`calendar_api.js`가 export하는 실제 함수명은 `calendarEventsListAll`/`calendarColorsGet`), 색상 목록도 배열이 아닌 맵 형태여야 하는데 `Object.keys(...)`로 변환해 넘기고 있었습니다. 실제 API 함수를 호출하고 올바른 색상 맵을 전달하도록 수정했습니다.
*   **`calendar_engine.js`/`calendar_categories.js`의 미선언 변수 `appSettings`**: 어디에도 선언되지 않은 전역 변수를 참조해 캘린더 분류 실행 시 `ReferenceError`로 즉시 중단되던 문제를 `SettingsStore.getSettings()` 호출로 수정했습니다.
*   **존재하지 않는 `throttleGeminiCall` 호출**: `calendar_categories.js`가 정의된 적 없는 함수를 호출해 캘린더 카테고리 생성이 항상 실패했습니다. 해당 래퍼 호출을 제거했습니다.
*   **캘린더 탭 i18n 키 누락**: 옵션 페이지 Calendar 탭에서 쓰는 13개 번역 키(`optionsMenuCalendar`, `calendarPanelDesc` 등)가 4개 언어 `messages.json`에 전혀 없어 번역 대신 키 이름이 그대로 노출되던 문제를 모든 로케일에 키를 추가해 수정했습니다.
*   **AI 라우터 성공 시 상태 저장 누락**: `ai_request_router.js`가 실패했던 키가 복구됐을 때 상태를 `"Ready"`로 되돌리는 로직이, 저장 시점에 서로 다른 두 번의 설정 조회 결과를 섞어 써서 실제로는 저장되지 않던 문제를 수정했습니다.

## 6. 통합 오류 수정 (AI Credential 일원화 / Calendar Router 우회 제거 / Failover 정책 정교화)

README에 "완료"라고 적혀 있던 내용을 실제 코드 기준으로 재검증하여 발견한 구조적 불일치와 런타임 결함을 수정했습니다. 상세 내역은 커밋 로그를 참고하세요.

*   **AI Credential 구조 일원화**: `popup.js`, `dashboard.js`가 여전히 구형 `ai.geminiApiKeys` / flat `geminiApiKeys` storage key를 읽고 쓰던 문제를 중앙 `ai.credentials` 구조로 통일했습니다. Popup은 이제 활성 Credential 수·Provider·모델·상태를 함께 표시합니다.
*   **Calendar Category 생성이 AI Router를 완전히 우회하던 문제 수정**: `calendar_categories.js`가 Gemini API를 직접 `fetch()`하던 코드를 제거하고, Gmail 분류와 동일하게 `AIRequestRouter.generateStructured()`를 통해 Provider/모델 선택·재시도·Failover·Quota 정책을 공유하도록 했습니다. AI가 생성한 카테고리는 저장 전 스키마/허용 색상 검증을 거칩니다.
*   **Failover 정책이 실제로 반영되지 않던 문제 수정**: `ai.requestPolicy`의 `retryEnabled`/`failoverEnabled`/`quotaAware`가 라우터 동작에 반영되지 않던 것을 고쳤습니다. Rate Limit은 이제 무조건 다음 키로 넘어가지 않고 우선 Retry-After만큼 대기 후 재시도하며, Credential별 재시도 횟수가 다음 Credential에 누적되지 않습니다.
*   **오류 분류 정교화**: HTTP 429/400을 무조건 quota/API Key 오류로 단정하던 로직을 응답 본문의 명시적 신호를 우선 확인하도록 바꾸고, 400은 `invalid_request`로 분리해 정상 Credential이 잘못 비활성화되지 않게 했습니다.
*   **Provider별 Structured Output 형식 차이 대응**: 저장소 전체가 공유하는 schema(Gemini 스타일 대문자 타입)를 OpenAI strict `json_schema`(표준 소문자 JSON Schema)로 자동 변환하는 정규화 로직을 추가했습니다. Anthropic 응답은 코드펜스/설명 텍스트가 섞여도 JSON을 추출할 수 있도록 파싱을 강화했습니다.
*   **Quota 상태의 서비스 워커 재시작 대응**: 메모리에만 있던 Quota/Rate-limit 상태를 `chrome.storage.local`에도 최소 정보로 백업해, 서비스 워커가 재시작되어도 이미 소진된 Credential을 곧바로 재시도하지 않도록 했습니다.
*   **Calendar Category 매칭 fallback 수정**: AI가 알 수 없는 카테고리명을 반환하면(과거엔 존재하지 않는 "기타" 카테고리를 하드코딩해서 항상 실패 처리) 이제 `unclassified`로 별도 집계하고, 존재하지 않는 카테고리를 만들어내지 않습니다. 실행 중 오류가 나도 이미 반영된 색상 변경분(부분 성공)은 그대로 결과에 남습니다.
*   **사용자 지정 캘린더 색상 보호**: 사용자가 옵션 페이지에서 카테고리 색상을 직접 바꾸면 `colorSource: "user"`로 표시되고, 이후 AI로 카테고리를 다시 생성해도 그 색상은 덮어쓰지 않습니다.
*   **Google Drive 백업/복원이 새 중앙 설정을 반영하지 않던 문제 수정**: v1/v2 시절 flat key만 백업하던 로직을 `appSettings`(ai.credentials, google.oauth 포함) 전체를 백업하도록 확장했습니다. API Key/Client Secret 등 민감 정보는 기본 백업본에서는 제거되고, "자격 증명 포함" 옵션을 켰을 때만 암호화 대상에 포함됩니다.
*   **문구 수정**: 언어 선택 드롭다운에서 "System Default" 항목을 제거했습니다(언어는 4개 지원 언어 중 하나로 저장되며, 마이그레이션/최초 설치 시 브라우저 언어로 자동 결정됩니다). "Client Secret (Optional)"을 "Client Secret"으로 수정했습니다.

### 알려진 제한 사항 (Known Limitations)

다음 항목은 이번 수정에서 다루지 않았으며, 실제 코드가 아직 요구사항을 완전히 만족하지 못합니다. 향후 별도 작업이 필요합니다.

*   **모델 목록 동적 조회 미구현**: `AIProviderRegistry.SUPPORTED_MODELS`는 여전히 정적 하드코딩 목록입니다. Provider별 `listModels(apiKey)` 같은 동적 조회는 구현되지 않았습니다.
*   **Gmail 분류 배치/스로틀링이 Gemini 전용 상수에 고정**: `background.js`의 `GEMINI_RPM_LIMIT` 등은 여전히 전역 상수로 배치 크기와 호출 간격을 계산합니다. 여러 Provider별로 다른 rate limit을 반영하려면 이 계산을 Provider metadata 기반으로 재설계해야 하는데, 기존 Gmail 자동 분류 동작을 깨뜨릴 위험이 커서 이번 작업 범위에서 제외했습니다.
*   **Side Panel 자동 활성화/비활성화 로직 미검증**: Gmail 탭 감지, SPA 라우팅 대응, `chrome.sidePanel` API 제약 준수 여부는 이번에 별도로 검토하지 않았습니다.
*   **Calendar PATCH 동시성/백오프 미구현**: 이벤트별 색상 PATCH는 여전히 순차 처리이며, 429/5xx에 대한 재시도·동시성 제한은 추가하지 않았습니다.
*   **Options 섹션별 오류 격리(safeInit) 미구현**: 특정 탭 초기화 중 예외가 나면 이후 탭 초기화가 중단될 수 있는 구조가 그대로 남아 있습니다.
*   **API Key 저장 시 암호화 미적용**: `ai.credentials[].apiKey`는 여전히 평문으로 `chrome.storage.local`에 저장됩니다.
*   **실제 Chrome 수동 테스트 미실행**: 이 저장소는 정적 코드 검증(`node --check`, i18n 키 대조)만 수행했으며, 실제 Chrome에 로드해 Settings/AI/Calendar/Side Panel/Popup 전체 시나리오를 수동으로 확인하지 못했습니다. 배포 전 최소한 아래 절차로 수동 검증이 필요합니다: Options의 모든 탭 클릭, 4개 언어 전환, Gemini/OpenAI/Anthropic 각각 키 등록 후 분류 1회 실행, 우선순위 다른 Credential 2개로 Failover 확인, Calendar Category 생성 및 색상 적용, Popup 상태 표시 확인.

## 7. 정적 수정 2차 (실제 Chrome 없이 코드로 검증 가능한 구조적 결함 제거)

실제 Chrome/Gmail 접속 없이 코드만으로 검증 가능한 범위에서 추가로 발견한 결함을 수정했습니다.

*   **Router retry 소진 후 failover 실패**: `AIRequestRouter`가 재시도 횟수를 다 쓴 뒤에도(rate_limit/server_error가 "retry" 판정이었다는 이유로) 다음 Credential로 넘어가지 않고 전체 작업을 종료하던 버그를 수정했습니다. 이제 Credential 하나당 `1 + maxRetries`번 시도한 뒤, `failoverEnabled` 정책에 따라 다음 Credential로 넘어가거나 즉시 종료합니다.
*   **AIQuotaManager 초기화 race**: 서비스 워커가 막 재시작된 직후 quota 상태 복원(`chrome.storage.local` 읽기)이 끝나기 전에 `isAvailable()`이 판단을 내릴 수 있던 문제를 수정했습니다. `isAvailable()`을 async로 바꾸고, `AIRequestRouter`가 매 요청 시작 시 `AIQuotaManager.initialize()`를 await하도록 했습니다.
*   **Migration이 존재하지 않는 모델 ID를 생성하던 문제**: v2→v3 마이그레이션이 `${providerId}-default-model` 같은 실제로 존재하지 않는 모델 ID를 만들어낼 수 있었습니다. 이제 `AIProviderRegistry`에 등록된 실제 모델 중에서만 fallback을 선택하고, 유효한 모델이 없으면 `model: null, modelNeedsSelection: true`로 표시합니다. `AIKeyManager.getActiveCredentials()`는 모델이 정해지지 않은 Credential을 활성 목록에서 제외합니다.
*   **Provider 간 schema 표기 불일치**: 저장소 전체가 공유하는 schema가 Gemini 스타일(대문자 "OBJECT"/"STRING")과 표준 JSON Schema(소문자)가 혼용되고 있었습니다. Google Provider가 어떤 표기로 들어와도 대문자로 정규화해 보내도록 수정했습니다(OpenAI 쪽 소문자 정규화는 1차 수정에서 이미 반영).
*   **Options 왼쪽 Navigation 및 각 탭 제목의 i18n 누락**: 왼쪽 메뉴 9개 항목과 Connections/Gmail/Automation/Notifications/Data/Advanced 탭의 카드 제목 다수가 `data-i18n` 없이 영어로 하드코딩되어 있었습니다. 해당 요소에 `data-i18n`을 추가하고 4개 언어 메시지를 채웠습니다. (각 탭 내부의 세부 label/버튼/placeholder 전체를 훑는 완전한 감사는 범위가 커서 이번 라운드에는 다 담지 못했습니다 - 아래 "알려진 제한 사항" 참고)
*   **죽은 코드 정리**: 실제로는 아무 곳에서도 참조되지 않던 `GEMINI_MODEL`, `lastGeminiCallAt`, `currentCallIntervalMs`, `MAX_CALL_INTERVAL_MS`, `INTERVAL_BACKOFF_MULTIPLIER`, `INTERVAL_RECOVERY_MULTIPLIER`, `DAILY_QUOTA_TEXT_PATTERN`, `GEMINI_REQUEST_TIMEOUT_MS`와, 실제로는 존재하지 않는 함수를 가리키던 `throttleGeminiCall()` 주석을 제거했습니다. `callGeminiForJson`은 이미 `AIRequestRouter` wrapper였으므로 `callAiForJson`으로 이름만 정리했습니다.
*   **Credential Test 구조 확인**: 옵션 페이지의 "Test Connection"은 이미 저장 전 form 값으로 Provider를 직접 검증하는 구조였고(Router/Quota를 거치지 않음) 별도 수정이 필요하지 않았습니다.

### 알려진 제한 사항 (2차, MANUAL/E2E REQUIRED 포함)

*   **Dynamic Model Discovery 미구현**: `AIProviderRegistry.SUPPORTED_MODELS`는 여전히 정적 목록입니다. Provider별 `discoverModels(credential)` API 조회, 모델 캐시(TTL), loading/empty/error 상태 UI는 구현하지 않았습니다.
*   **Options i18n 완전 감사 미완료**: 왼쪽 Navigation과 각 탭의 주요 제목은 번역되지만, 세부 label/버튼/placeholder 전체를 훑는 완전한 감사는 하지 않았습니다.
*   **AI Provider fetch에 timeout 없음**: `google_provider.js`/`openai_provider.js`/`anthropic_provider.js`의 `fetch()` 호출에는 명시적 timeout/AbortController가 없어, 네트워크가 응답을 주지 않으면 요청이 무기한 대기할 수 있습니다.
*   **Gmail 분류 배치/스로틀링이 Gemini 전용 상수에 고정** (1차와 동일 - 미해결).
*   **MANUAL/E2E REQUIRED**: 실제 Gmail 접속·OAuth 로그인/해제·Side Panel 자동 열림/닫힘·실제 Gemini/OpenAI/Anthropic API 호출·실제 model discovery·실제 quota/Retry-After 응답은 이 환경에서 검증하지 못했습니다.

## 8. PDF 번역: 스캔본 OCR과 번역 이어하기

### 스캔본 OCR

스캔된 이미지 PDF는 텍스트 레이어가 없어서 추출 단계에서 세그먼트가 0개로 나오고, 번역할 것이 없다는 경고만 남았습니다. 이제 그런 쪽을 이미지로 렌더해 OCR로 읽습니다.

*   **로컬 WASM(tesseract.js)을 씁니다.** 클라우드 OCR API는 키를 하나 더 요구하고, 멀티모달 LLM에 페이지 이미지를 던지는 방식은 스캔본 100쪽이면 OCR 비용이 번역 비용을 넘습니다. 로컬 WASM은 공짜이고 원문이 밖으로 나가지 않습니다.
*   **판정은 쪽 단위입니다.** 추출된 글자 수가 임계값(기본 16자)보다 적은 쪽만 OCR 대상으로 표시하고, 그 목록이 확정된 뒤에 두 번째 패스로 OCR합니다. 쪽당 1~3초가 드는 작업이라 "정말 필요한 쪽"만 골라야 합니다. `강제` 모드는 텍스트가 있어도 모든 쪽을 OCR하고, 그 쪽의 텍스트 레이어 세그먼트는 버립니다(같은 자리에 번역문이 두 번 찍히는 것을 막습니다).
*   **원문을 배경색으로 덮습니다.** 스캔본의 원문은 텍스트가 아니라 이미지 픽셀이라 redaction으로는 지울 수 없습니다(지울 텍스트 자체가 없습니다). 상자 주변 픽셀의 **중앙값**으로 배경색을 뽑아 그 색 사각형으로 덮은 뒤 번역문을 올립니다. 평균이 아니라 중앙값을 쓰는 이유는 테두리에 이웃 글자나 표 선이 걸려도 색이 끌려가지 않게 하려는 것이고, 흰색으로 고정하지 않는 이유는 누런 스캔본에서 흰 사각형이 도드라지기 때문입니다. 배경이 어두우면 글자색을 흰색으로 뒤집습니다.
*   **덮기는 전부 먼저, 글쓰기는 나중에** 한 콘텐츠 스트림에 넣습니다. 항목별로 번갈아 넣으면 상자가 겹칠 때 뒤 항목의 배경이 앞 항목의 번역문을 지웁니다.
*   **좌표는 `zoom` 하나로 되돌립니다.** OCR 상자는 픽셀 좌표이고 재구성에 필요한 것은 페이지 공간(pt)입니다. 래스터화에 쓴 배율과 픽스맵 원점만 알면 되돌릴 수 있습니다. 해상도는 상한을 둡니다(기본 300DPI, 4천만 픽셀). A0 도면 같은 큰 페이지에서 그대로 곱하면 픽스맵 하나가 수백 MB가 되어 WASM 힙이 먼저 죽습니다.
*   **신뢰도 45 미만 문단은 버립니다.** 스캔 잡티를 글자로 읽은 것들인데, 남기면 번역 비용을 쓰면서 원본 그림 위에 헛소리 상자를 그립니다.
*   **OCR을 쓸 수 없어도 작업은 계속됩니다.** `vendor/tesseract`가 없거나 언어 데이터가 없으면 그 사실을 로그에 남기고, 텍스트 레이어가 있는 나머지 쪽은 그대로 번역합니다. 번역 대상이 0개일 때의 안내 문구도 원인별로 갈라 놓았습니다(스캔본인데 OCR이 꺼져 있음 / OCR이 글자를 못 찾음 / 범위에 문장이 없음).
*   바이너리는 mupdf와 같은 이유로 저장소에 넣지 않습니다. 받는 방법과 폴더 모양은 `Gmaillabeler/vendor/README.md`에 있고, `pdf/testdata/selftest.html`의 "OCR 점검"이 설치를 확인해 줍니다.

### 번역 이어하기 (세그먼트 번역 캐시)

10분짜리 번역이 중지·할당량 소진·서비스워커 종료로 끊기면 진행분이 전부 사라졌습니다. 별도의 재개 상태 기계를 두는 대신 **내용 주소 방식 캐시** 하나로 해결했습니다.

*   **키 = `(원문 + 번역에 영향을 주는 옵션)`의 SHA-256.** 배치에 성공하는 즉시 번역문을 캐시에 적어두면, 같은 문서를 같은 조건으로 다시 돌릴 때 이미 번역한 세그먼트는 조회로 채워지고 남은 구간만 API를 씁니다. 중지든 할당량 소진이든 워커가 죽은 것이든 구분 없이 같은 방식으로 이어집니다.
*   **캐시 저장은 배치마다** 합니다. 문서 끝에서 한 번에 적으면 그 전에 워커가 죽었을 때 그 실행의 진행분이 남지 않습니다.
*   **키에 문서 id를 넣지 않습니다.** 그래서 문서 안에서 반복되는 머리말/꼬리말/표 헤더가 한 번만 번역되고, 같은 파일을 다시 올려도(docId가 새로 발급됩니다) 캐시가 그대로 맞습니다.
*   **번역 결과와 무관한 옵션은 키에서 뺐습니다.** 배치 크기·페이지 범위·글자 크기 배율·OCR 설정을 바꿨다고 이미 번역한 문단을 다시 살 이유가 없습니다. 반대로 번역 언어·문체·용어 정책·프롬프트 프로파일이 바뀌면 키가 달라져 다시 번역합니다.
*   **실패는 기억하지 않습니다.** 원문 유지로 강등된 세그먼트를 캐시에 적으면 다음 실행이 영원히 원문을 쓰게 됩니다.
*   **직전 문맥에 캐시 히트도 포함됩니다.** 이어한 실행은 실제로 API를 타는 세그먼트가 문서 중간부터 시작하는데, 그때 문맥이 비어 있으면 앞부분에서 정한 용어와 어긋난 번역이 나옵니다. 문맥은 이제 "문서 순서상 앞에 있고 이미 번역된 세그먼트"에서 모읍니다.
*   **화면**: 최근 번역 목록의 완료되지 않은 실행에 `이어하기` 버튼이 붙고(워커가 죽어 `진행중`으로 굳은 기록도 포함), 결과 카드와 진행 상태에 캐시 재사용 건수가 보입니다. 세부 설정에서 캐시를 끄거나(재번역) 비울 수 있습니다. 캐시는 2만 건 상한으로 오래된 것부터 정리합니다.
*   **중지가 OCR에도 닿습니다.** 추출/OCR은 오프스크린에서 돌아 `isCancelled()`를 볼 수 없으므로, 서비스워커가 중지 플래그를 폴링해 엔진에 `abort`를 보냅니다. OCR 루프는 쪽 경계에서 멈추고 그때까지 읽은 문단을 돌려줍니다.

### 같이 고친 것

*   **`patchPdfRun()`이 항상 실패하던 문제**: 정의는 `(runId, patch)` 두 인자인데 호출부 5곳이 모두 객체 하나를 넘기고 있어서, `store.get(객체)`가 IndexedDB `DataError`로 터졌습니다. PDF 번역이 첫 단계에서 예외로 끝나던 원인입니다. 호출부 표기가 자연스러우니 정의를 객체 하나로 맞췄습니다.
*   **없는 레코드 조회가 truthy를 돌려주던 문제**: `pdf_db.js`의 트랜잭션 헬퍼가 `value !== undefined`로 상자를 벗겼기 때문에, 조회가 빗나가면(value가 `undefined`) 상자 객체 자체가 반환되고 그것은 truthy였습니다. 그래서 `if (!doc) 없음 처리` 검사가 전부 통과해 "문서를 찾을 수 없습니다" 대신 몇 줄 뒤에서 `TypeError`가 났습니다. 상자에 심볼 표를 달아 구분합니다.
*   **부분 완료 판정**: 원문 유지 세그먼트가 있는 실행도 `partial`로 남깁니다. 그래야 화면이 이어하기를 띄울 근거가 생깁니다.

### 알려진 제한 사항

*   **덮기는 단색입니다.** 배경에 그라데이션이나 그림자가 있으면 덮은 사각형이 보입니다. 상자 안의 배경 무늬도 함께 덮입니다.
*   **세로쓰기 OCR은 검증하지 않았습니다.** tesseract의 세로쓰기 모델(`*_vert`)을 쓰지 않고, 문단 상자를 가로쓰기로 가정해 다시 접습니다.
*   **문단 병합은 tesseract의 판단을 그대로 씁니다.** 다단 편집 스캔본에서 단이 잘못 묶이면 번역 단위도 그렇게 묶입니다.
*   **캐시는 문단 단위 정확 일치입니다.** 같은 문장을 담은 다른 문서는 같은 번역문을 씁니다(번역 메모리의 통상적인 동작). 한 글자만 달라도 캐시는 맞지 않습니다.
*   **MANUAL/E2E REQUIRED**: 실제 mupdf/tesseract WASM 바이너리를 띄운 검증은 이 환경에서 하지 못했습니다(둘 다 저장소에 없습니다). 순수 로직(캐시 키·이어하기 흐름·OCR 결과 정리·배경색 표본·재구성 콘텐츠 스트림·추출+OCR 두 패스·중지)은 mupdf/tesseract/chrome을 대역으로 바꿔 끼운 Node 테스트로 확인했습니다.

## 9. 사이드패널: 거짓말하는 타일 걷어내기 (0단계)

타일을 더 얹기 전에, 지금 있는 타일이 정직한지부터 맞췄습니다. 코드를 대조해 보니 **타일 59개 중 30개가 등록되지도 않은 작업을 가리키고** 있었습니다.

### 왜 아무도 몰랐나

세 가지가 겹쳐 있었습니다.

*   **컨텍스트 헤더가 HTML에서 통째로 빠져 있었습니다.** `ui/context.js`가 갱신하는 `contextService`/`contextTitle`/`contextDesc`/`dynamicActions` 네 요소가 `sidepanel.html`에 없었습니다(`5a22cd3 sidepanel ui` 개편 때 사라졌고 CSS만 남아 있었습니다).
*   그 결과 **`setActionFeedback()`이 허공에 썼습니다.** 이 함수는 `#contextDesc`에 문장을 넣는데, 그 요소가 없으니 "작업을 요청 중입니다", "오류: 지원하지 않는 작업 유형입니다" 같은 메시지가 한 번도 화면에 뜬 적이 없습니다. 죽은 타일을 눌러도 **정말로 아무 일도 일어나지 않았습니다.**
*   페이지별 빠른 실행 버튼(`ACTION_REGISTRY`)도 `#dynamicActions`에 그려지므로 함께 죽어 있었고, 그래서 `gmail_classify_thread`·`gmail_summarize_thread`(열어 둔 메일 한 통만 분류/요약)는 **접근 경로 자체가 없었습니다.**

### 고친 것

*   **컨텍스트 바 복구**: `panelContainer` **바깥**에 새로 만들었습니다. 안에 두면 워크스페이스를 그릴 때마다 `innerHTML`을 비우므로 화면을 바꿀 때마다 사라집니다(예전 구조가 그랬습니다). 지금 무엇을 보고 있는지, 방금 무슨 일이 일어났는지, 이 화면에서 바로 할 수 있는 것 — 세 가지를 이 한 줄이 말합니다.
*   **작업 메시지는 잠시 떴다가 원래 설명으로 돌아갑니다.** 되돌리지 않으면 마지막 작업 메시지가 영구히 남아 "지금 무엇을 보고 있는지" 자리를 잡아먹습니다.
*   **타일에 상태를 선언합니다.** `status: "planned"`(아직 안 만듦) / `"unavailable"`(만들 수 없음)과 사람이 읽을 `note`, 그리고 `needsScope`(필요한 권한)를 registry에 적었습니다. 회색으로 그리고, 누르면 **왜 안 되는지 본문에 안내 카드**가 뜹니다. 침묵이 최악의 응답입니다.
*   **선언과 실제를 대조하는 안전망**(`nav/tile_state.js`): 사이드패널이 뜰 때 백그라운드에 `job.listTypes`를 한 번 물어, "된다"고 적힌 타일이 실제로 등록된 작업을 가리키는지 확인합니다. 어긋나면 "확장 오류"로 표시합니다. 목록을 못 받으면(서비스워커가 자는 중 등) 검사를 건너뜁니다 — 확인 못 했다는 이유로 멀쩡한 타일을 막으면 그게 더 나쁩니다.
*   **숨어 있던 기능 6개를 꺼냈습니다.** 백그라운드에 이미 등록되어 동작하는데 사이드패널에 문이 없던 것들입니다: 반복분류 · 중복정리 · 라벨색상 · 캘린더 카테고리생성 · 설정백업 · 설정복원.
*   **정의가 없던 타일 2개(캘린더 동기화·알림설정)는 삭제했습니다.** 무슨 일을 하는 타일인지 아무도 정의한 적이 없습니다.
*   **i18n 누락 5건**: `sidepanelSummarizeAll`, `sidepanelClassifyThread`, `sidepanelSummarizeThread`, `sidepanelClassifySchedule`, `sidepanelApplyColors`가 4개 언어 전부에 없었습니다. 컨텍스트 헤더가 죽어 있어 드러나지 않았을 뿐, 살리자마자 버튼에 키 문자열이 그대로 찍혔습니다. 네 언어에 채웠습니다.

### 정정

기획 단계에서 "캘린더 색상적용은 잡 등록 한 줄이면 살아난다"고 적었는데 **틀렸습니다.** `calendar_apply_colors`는 이미 등록되어 있었고(래퍼 함수 `registerCalendarClassifyJob("calendar_apply_colors", ...)`로 등록되어 `registerJob("` 문자열 검색에 걸리지 않았습니다) 그 타일은 원래 동작하고 있었습니다. 죽은 타일은 31개가 아니라 30개입니다.

## 10. 사이드패널: 이미 쌓인 데이터를 화면으로 (1단계)

새 권한도, 새로 모으는 데이터도 없습니다. 이미 저장되고 있는데 볼 곳이 없던 것들에 화면을 붙였습니다.

### 새 서비스 세 개

*   **작업(⏱️)** — 진행 중인 작업, 최근 기록, 로그, AI 사용량을 한 화면의 네 탭으로. 각각 `jobStatus`/`jobProgress`(이미 있음), `recentJobs`(**지금까지 팝업에서만** 보였음), `log_db`(**별도 탭 페이지에서만** 보였음), `ai_quota_manager`(**옵션 페이지에서만** 보였음)를 읽습니다. 로그는 레벨 필터와 검색을 달았습니다 — 작업이 실패했을 때 원인을 보려고 다른 페이지를 열지 않게 하는 것이 이 화면의 목적입니다.
*   **학습(🧠)** — 정정 패턴 목록(`A → B`, 누적 횟수, 예시, 자동 반영까지 남은 횟수)과 최근 분류 기록. **"지금 기준에 반영"** 버튼으로 임계값을 기다리지 않고 바로 적용할 수 있습니다. 자동 학습은 같은 정정이 5번 반복되어야 도는데, 사용자가 직접 시키는 경우엔 그 추정이 필요 없습니다.
*   **AI(✨)** — `Gemini` 서비스를 대체합니다. 공급자별 키 상태(정상/쿨다운/할당량 소진, 오늘 요청 수, 모델)와 **실제로 동작하는 프롬프트 실행기**. 예전 화면은 칩을 눌러도 문구만 바뀌었고 타일 3개는 등록된 적 없는 작업을 가리켰습니다.

### 공통 shell 추출

세 화면이 같은 조각을 쓰도록 `workspaces/shell.js`를 만들었습니다(`openWorkspace` / `section` / `statRow` / `emptyState` / `tabBar` / `badge` / `formatWhen` / `ask`). 0단계에서는 소비처가 없어 미뤘던 것을 소비처가 셋이 된 지금 뽑았습니다. 시간은 `formatWhen`으로 통일해 상대 표기("3분 전")를 쓰고, 하루가 넘으면 날짜로 바꿉니다.

### 같이 고친 것

*   **정정 패턴의 누적 횟수를 잃던 문제**: `count`는 자동 학습이 반영될 때 0으로 초기화됩니다(다음 반영까지 다시 세기 위해). 그래서 "지금까지 몇 번 고쳤는지"를 알 방법이 없었습니다. 초기화하지 않는 `totalCount`를 추가했습니다. 옛 기록은 그 시점의 `count`를 시작값으로 삼습니다.
*   **패턴 전체를 읽을 방법이 없던 문제**: `getCorrectionPattern(key)`는 키 하나만 조회합니다(분류 도중 확인용). 목록을 위해 `getAllCorrectionPatterns()`를 추가했습니다.
*   **존재하지 않는 M3 토큰에 기대던 색**: `--md-sys-color-tertiary-container`는 이 저장소에 정의된 적이 없습니다. 그런데 경고 표시가 그 토큰을 쓰고 있어서 `surface-variant`로 폴백되어, **"정상"과 "쿨다운" 배지가 같은 회색으로 보였습니다**(키 상태를 한눈에 구분하는 것이 그 화면의 존재 이유인데). `--ws-good`/`--ws-warn` 토큰을 라이트·다크 각각 정의해 초록/호박/빨강으로 갈랐습니다. 같은 문제를 갖고 있던 `.pdf-warn`도 함께 고쳤습니다.
*   **프리셋 칩이 세로로 쌓이던 문제**: `.ai-chips-row`가 `flex-direction: column`이었습니다(칩 3개짜리 옛 화면 기준). 네 개를 세로로 쌓으면 입력창이 화면 밖으로 밀려서, 가로로 접히는 컴팩트 칩으로 바꿨습니다.

## 11. 메일 정리: 바꾸기 전에 보여준다 (2단계)

죽어 있던 `메일정리` 타일을 되살렸습니다. **잡이 아니라 화면으로** 만든 것이 이 작업의 핵심입니다 — 무엇을 옮길지 고르지 않고 클릭 한 번으로 수백 통을 처리하는 버튼은, 되돌리기가 있어도 만들지 않습니다.

### 흐름

조건 고르기 → **미리보기** → 목록에서 제외 → 고른 것만 적용 → 되돌리기.

*   **조건은 Gmail 검색에 맡깁니다.** 읽은 지 오래됨 / 프로모션 / 소셜 / 알림 / 큰 첨부 / 특정 발신자 / 특정 라벨을 골라 `(A) OR (B)` 로 합치고, 보호 조건은 AND로 바깥에 붙입니다. 수천 통을 확장으로 끌어와 걸러내면 요청 수와 시간이 폭발하는데, 같은 판정을 서버가 이미 해줍니다.
*   **별표·중요 표시는 기본으로 제외합니다.** 사용자가 "이건 남긴다"고 직접 표시한 것입니다.
*   **미리보기는 아무것도 바꾸지 않습니다.** 조건에 맞는 개수(최대 500까지 셈)와 앞쪽 60통의 제목·발신자·날짜·크기를 보여줍니다. 본문은 받지 않습니다(`format=metadata`) — 60통의 본문을 받으면 그것만으로 몇 초가 걸립니다.
*   **적용은 조건을 다시 검색하지 않습니다.** 사용자가 확인한 id에만 적용합니다. 미리보기와 적용 사이에 새 메일이 들어와 대상이 달라지는 일이 없어야 합니다.
*   **확인하지 못한 분량은 두 번 물어봅니다.** 목록에 표시한 것보다 많이 걸렸을 때만 "전체 처리" 버튼이 나타나고, 한 번 누르면 빨간 확인 상태로 바뀌어 다시 눌러야 실행됩니다. 목록에서 일부러 제외한 메일은 "전체"에서도 빠집니다 — 그 말 때문에 다시 포함되면 사용자의 의도를 배신하는 것입니다.

### 되돌릴 수 있는 일만 합니다

영구 삭제는 하지 않습니다(할 수도 없습니다 — `gmail.modify` 권한으로는 휴지통까지입니다). 세 가지 처리 방식 모두 역연산이 있습니다.

| 처리 | 실제 동작 | 되돌리기 |
|---|---|---|
| 보관 | `batchModify` 로 `INBOX` 제거 (1000통당 요청 1회) | `INBOX` 재부착 |
| 휴지통 | `messages/{id}/trash` (메일당 요청 1회) | `messages/{id}/untrash` |
| 라벨만 | `batchModify` 로 라벨 추가 | 그 라벨 제거 |

**휴지통에 `batchModify`를 쓰지 않은 이유**: `TRASH`를 라벨처럼 붙이는 것이 문서상 보장되지 않습니다. 실제 Gmail로 시험해볼 수 없는 환경이라, 동작이 확실한 문서화된 엔드포인트만 씁니다. 대신 메일당 요청이 하나씩 필요해 한 번에 200통으로 제한하고, 그 상한을 넘으면 "전체 처리" 버튼을 아예 비활성화합니다 — 확실히 실패할 버튼을 두 번 누르게 하는 것은 안내가 아니라 함정입니다.

### 같이 고친 것

*   **`0`을 입력하면 최솟값이 아니라 기본값으로 튀던 문제**: `Number(x) || 기본값` 꼴은 `0`이 falsy라서, "0MB 이상"이라고 적으면 5MB가 됩니다. 빈 칸·문자쓰레기(→기본값)와 범위를 벗어난 숫자(→경계값)를 구분하는 `clampNumber`를 씁니다.
*   **`action` 키 충돌**: 라우터는 `request.action`으로 액션 이름을 받는데, 정리 방식(`archive`/`trash`/`label`)도 같은 키에 담으려 했습니다. 처리 방식은 `request.mode`로 분리했습니다.

### 알려진 제한 사항

*   **조건 일치 개수는 500까지만 셉니다**(한 페이지). 그보다 많으면 `500+`로 표시합니다.
*   **전체 처리도 500통까지입니다**(세어둔 id만 처리). 그 이상은 여러 번 실행해야 합니다.
*   **되돌리기는 마지막 한 번만** 기억합니다(최대 1000통). 두 번 정리하면 첫 번째는 되돌릴 수 없습니다.
*   **분류 작업 중에는 적용이 막힙니다.** 그쪽도 같은 메일의 라벨을 건드려서, 겹치면 "분류가 방금 붙인 라벨을 정리가 떼는" 순서 문제가 생깁니다.

### 검증

Gmail API를 대역으로 바꿔 끼운 Node 테스트 34건을 통과했습니다 — 질의 조립(OR 묶기, 보호 조건, 값 없는 규칙 제외, 범위 clamp), 미리보기가 아무것도 바꾸지 않음(POST 0건), 적용이 조건을 다시 검색하지 않음, 세 방식의 정확한 API 호출 형태, 1000개 분할, 휴지통 상한 거부, 세 방식 각각의 역연산, 되돌리기 후 기록 삭제. UI는 Chromium에서 전체 흐름을 눌러 확인했습니다 — 236통 일치 중 12통 표시, 2통 제외 시 "표시된 10통 보관"으로 바뀜, 전체 처리 1차 클릭에 요청 0건, 적용된 id가 정확히 10건, 되돌리기 후 기록 비워짐, 휴지통 상한 초과 시 버튼 비활성.

## 12. 번역 용어집: 이미 있던 자리를 채우다

번역 프롬프트는 **처음부터** 용어집을 받도록 되어 있었습니다(`{{glossary_data}}`, 그리고 8절 GLOSSARY RULES 전체). 그런데 그 값을 넣을 화면이 없어서 항상 `(no glossary provided)`가 들어갔습니다. 프롬프트 쪽은 한 줄도 손대지 않고 입력 경로만 만들었습니다.

### 표 편집기가 아니라 텍스트 상자인 이유

용어집은 보통 스프레드시트나 기존 문서에서 통째로 가져옵니다. 400px짜리 사이드패널에서 입력칸 20쌍을 하나씩 채우게 하는 것보다, 붙여넣고 한 번에 고치는 편이 실제 번역 작업 방식입니다. 대신 **무엇으로 읽혔는지를 바로 아래에 계속 보여줍니다** — 자유 텍스트를 받으면서 해석 결과를 감추면 사용자는 자기가 뭘 적었는지 알 수 없습니다.

받아들이는 줄 모양:

```
machine learning => 기계 학습        (=>, ->, → 모두 가능)
throughput => 처리량 [네트워크 문맥]   (대괄호는 비고)
API                                  (대상이 없으면 "번역하지 말 것")
원문<TAB>번역<TAB>비고                (스프레드시트에서 붙여넣기)
# 주석                               (무시)
```

같은 원문이 두 번 나오면 마지막 줄이 이기고, 그 사실을 경고로 알립니다. `정리` 버튼은 중복을 없앤 결과로 텍스트를 다시 씁니다.

### 프로필

문서 종류마다 용어 규칙이 다릅니다(기술문서와 계약서). 하나로 합치면 "이 문서에는 해당 없는 규칙"이 프롬프트에 계속 실려 토큰만 씁니다. 그래서 프로필로 나누고, 번역 화면의 세부 설정에서 골라 씁니다.

### 프로필 id만 저장하고 실행할 때 읽습니다

번역 옵션에는 `glossaryProfileId`만 담고, 실행 직전에 `bg/features/pdf/index.js`가 그것을 텍스트로 바꿔 넣습니다. 화면이 텍스트를 직접 보내면 **이어하기**가 깨집니다 — 이어하기는 저장된 옵션을 그대로 다시 쓰는데, 옛 용어집 텍스트가 박혀 있으면 그 사이 고친 용어집이 반영되지 않습니다.

### 용어집을 고치면 캐시가 무효가 됩니다

`glossaryText`는 번역 캐시 키에 들어갑니다(8장 참고). 그래서 용어를 바꾸면 다음 실행에서 그 조건의 문단을 다시 번역합니다. **의도된 동작입니다** — 용어를 고쳤는데 옛 번역문을 캐시에서 꺼내 쓰면 고친 의미가 없습니다. 화면에도 그 사실을 적어 두었습니다.

### 같이 고친 것

*   **미리보기가 편집 전 내용을 보여주던 문제**: "번역할 때 실제로 전달되는 내용"이라고 적어놓고 첫 렌더 시점의 파싱 결과를 그대로 두고 있었습니다. 입력할 때 통계와 경고만 다시 그리고 미리보기는 빼먹은 탓입니다 — 그 문구가 거짓말이 되므로 함께 갱신하도록 고쳤습니다.

### 검증

Node 테스트 30건을 통과했습니다 — 파싱 20건(화살표 세 종류, 탭 구분, 번역 금지 표현, 비고 분리, 중복·대소문자, 길이·개수 상한, 파싱→텍스트→파싱 왕복), 저장소 10건(빈 상태, 상한, 망가진 저장값, 지워진 프로필을 가리키는 활성 id, 프로필 수정이 즉시 반영, **용어집이 바뀌면 캐시 키가 실제로 달라지는지**). UI는 Chromium에서 프로필 생성 → 편집 → 자동 저장 → 중복 경고 → 정리 → 번역 화면에서 선택 → 재진입 후 선택 유지까지 눌러 확인했습니다.
